# MVP-0 推荐规则

> 这份文件是 Recommendation Agent 的判定依据，也是 `tools/donghu_demo.py` 里规则引擎的文字版。
> **两者必须一致。** 改了规则就要同时改代码，然后跑 `python3 tools/validate_demo_data.py`。

## 为什么要把规则写死

PRD v0.4.1 定义了要展示什么（SEND / NO_SEND / Before / After），但没有定义"凭什么"。
没有成文规则时，同一条内容跑三次会得到三份不同的名单，彩排就无法收敛，
表里预置的 Before 状态也对不上 Agent 的实时输出。

所以 MVP-0 用一套**可以手算、可以复核**的规则，而不是让模型自由发挥。

## 规则和 Agent 的分工

推荐不是纯规则，也不是纯模型，而是分层的：

```text
确定性规则  →  eligibility 与硬排除，产出候选集合
Agent       →  在候选集合内做语义判断（服务能力核对、文案）
运营        →  最终确认后才触达
```

**规则不负责"决定发给谁"的全部。** 它负责把 25 个人收敛成一个可解释的候选集合，
并把绝不能发的人挡住。服务类内容还需要 Agent 做能力级核对（第 5 步），
那部分无法硬编码，也不应该硬编码——把"上门助浴 ≠ 老人陪诊"写成规则表，
等于把每一种服务能力的组合都枚举一遍，既做不完也没必要。

因此 `tools/validate_demo_data.py --explain` 的输出：

- 对**非服务类内容**是最终标准答案，Agent 的结果应当完全一致；
- 对**服务类内容**（`commercial_level = service`）是候选基线，
  Agent 在此之上还会剔除能力对不上的人，结果可以更窄，但不应更宽。

## 三层语义

```text
ELIGIBLE     内容与居民适配（规则判定）
HOLD         适配，但今日不应主动触达
TARGET_TODAY = ELIGIBLE − HOLD    ← Push Plan.target_residents 只能由它生成
```

三层必须分开。Push Plan 是"今天准备发给谁"的执行草稿，
如果 HOLD 的居民还留在 `target_residents` 里，就会出现
"名单上有他、旁边又写着今天不要联系他"这种自相矛盾的输出。

但**被 HOLD 排除的人不能丢掉适配信息**：他明天可能就该收到这条内容。
所以 HOLD 单独成组展示，并单独写进 Push Plans 的 `hold_residents`。

## 判定顺序

对每一对（内容, 居民），按顺序执行。任何一步得出结论就停止。

### 第 0 步 · 内容门槛

内容不满足以下任一条，**整条内容不进入推荐**，不产生任何名单：

- `status` 必须是 `active`；
- `expire_at` **必须存在**；
- `expire_at` 必须晚于当前时间。

> `expire_at` 为空**不等于永不过期**，而是"时效无法判定"。
> 判定不了就不该推——活动结束几周后系统还在发，是最容易毁掉信任的那类错误，
> 而且完全无声。无法确定时效的内容应保留 `status = draft`，由运营补齐后再放行。
> 这一条由 Content Agent、规则引擎和校验脚本三处共同强制。

### 第 1 步 · 硬排除 → `NO_SEND`

命中任意一条即为 `NO_SEND`，并给出原因：

| 编号 | 条件 | 输出原因 |
|---|---|---|
| N1 | `居民.avoid_topics` ∩ `内容.topic_tags` ≠ ∅ | 命中 avoid_topics：<标签> |
| N2 | `居民.status = lost` | 居民状态为 lost |
| N3 | 该居民已有一条 `interaction_type = activity_signup` 且 `related_id` 等于本内容 | 已报名本条活动，不重复推送 |

N1 优先于一切正向证据。陈叔长期关注买菜生鲜，但只要内容带「优惠促销」标签就不发。

### 第 2 步 · 主题证据

计算居民与 `内容.topic_tags` 的交集，按以下四类收集证据：

| 编号 | 证据来源 | 性质 |
|---|---|---|
| E1 | `居民.recent_needs` | 近期 |
| E2 | `居民.recent_interests` | 近期 |
| E3 | 14 天内的 Interaction 的 `topic_tags`（负反馈类型不算） | 近期 |
| E4 | `居民.long_term_interests` | 长期 |

**一条证据都没有 → 不合格**，理由是"无任何主题依据"。

> 「不合格」和 `NO_SEND` 是两回事，不要混。
> `NO_SEND` = 本来有理由发，但被规则明确拦住，要说清楚为什么。
> 不合格 = 压根没有依据，不必解释，也不要列进 NO_SEND 名单。
> 25 个居民里通常有 17–20 人属于不合格，把他们全列出来会淹没真正的 NO_SEND。

### 第 3 步 · 人群门槛

若 `内容.target_population` 非空且不含「全部居民」：

- `居民.family_stage` ∩ `内容.target_population` ≠ ∅ → 通过；
- 否则，**只有近期证据（E1/E2/E3）可以覆盖人群不匹配**；
- 只有 E4（长期兴趣）而人群不匹配 → 不合格。

> 这一条是 Before/After 的承重墙。张姐是「普通家庭」，C003 面向「亲子家庭」，
> 所以她在 Before 阶段无论如何进不了名单；Quick Capture 产生 E2/E3 之后，
> 近期证据覆盖人群门槛，她才进得来。删掉这条覆盖规则，After 就不成立。

### 第 4 步 · 促销收紧

`内容.commercial_level = promotion` 时，必须有近期证据（E1/E2/E3）。
只有 E4 → 不合格。

> 对应运营原则"宁可少发"。长期爱买菜 ≠ 现在想看满减。

### 第 5 步 · 服务类内容

`内容.commercial_level = service` 时，该居民必须有一条**未满足**的 Need，
且 `need_category` 在 `内容.topic_tags` 内。

未满足 = `new` / `following` / **`unable_to_resolve`**。只有 `resolved` 才是真正关闭。

> `unable_to_resolve` 表示"当前没有供给"，不是"这件事不用办了"。
> 把它排除出匹配，会切断本项目最有价值的那条闭环：
>
> ```text
> 居民提出需求 → 暂时没有供给 → 沉淀为未满足需求
>             → 东湖据此引入服务 → 重新连接回原来有需求的人
> ```
>
> 王阿姨的上门助浴今天匹配不上，一个月后东湖真的引进了助浴服务，
> 她必须是第一批候选。否则"未满足需求是招商线索"就只是报表上的一句话。

**并且 Agent 还要做一次能力级核对**：Need 描述的具体事项必须真的在服务范围内。
类目相同不等于能办同一件事。

- 「上门助浴」≠「老人陪诊」（S006 是医院陪诊，不提供助浴）；
- 「空调清洗」≠「家庭大扫除」；
- 「修电饭煲」≈「小家电维修」（S003 明确列出电饭煲，可以匹配）。

类目对得上但能力对不上时，Need 应判为 `unable_to_resolve`，**不要硬凑一个服务**。
凑出来的匹配会在现场被一眼看穿，而且这正是"未满足需求 → 招商线索"这条价值线的来源。

### 第 6 步 · 通过 → `ELIGIBLE`

理由必须引用实际命中的证据，近期证据优先写在前面。

随后按 HOLD 拆成两组：

```text
TARGET_TODAY = ELIGIBLE − HOLD    进当天执行名单
HOLD                              内容适配，但今日暂停主动触达
```

## HOLD：今日不主动触达

与 SEND / NO_SEND **正交**，单独标记，不改变推荐判定本身。

条件（两条同时成立）：

1. `居民.status = low_active`；
2. 7 天内有 `interaction_type = negative_feedback` 的记录。

> 为什么要加 `status = low_active` 这个条件：
> 陈叔说的是"优惠消息少发一点"——针对某个主题，已经由 `avoid_topics` 表达，
> 他照样应该收到东湖早市。小刘说的是"最近消息有点多"——针对整体频率，
> 运营据此把他调成 `low_active`。只看"有没有负反馈"会把这两种情况混为一谈，
> 结果是把陈叔也停掉，那就变成了"一句抱怨就拉黑"，既不合理也不好解释。
>
> `status` 是运营的人工判断，让它参与规则，等于把"要不要整体降频"这个决定
> 留在人手里，符合"AI 只出 Draft"的原则。

HOLD 的处理方式：

- **从 `target_residents` 中排除**——当天不发；
- **保留在 `hold_residents` 中**，并写清原因——不丢失"内容其实适合他"这个判断；
- 出现在今日运营摘要的"今天不要主动触达"里。

HOLD 与 NO_SEND 的后续动作完全不同，所以不能混成一组：

| | 含义 | 明天怎么办 |
|---|---|---|
| `NO_SEND` | 这个主题对这位居民是禁忌 | 这个主题就不发了 |
| `HOLD` | 内容适配，只是此刻不该打扰 | 可以改日再发，或单独沟通 |

小刘的正确表达是：**"这条羽毛球活动其实挺适合他，但他刚说过消息太多，今天先不发。"**
不是"他不适合"，也不是"把他拉黑"。

## 边界说明

- **区域不参与 MVP-0 判定。** seed 里的 25 位居民都在东湖 15 分钟范围内，
  再叠一层区域匹配只会增加解释成本和出错面。区域取值仍然冻结在
  `config/vocabulary.md`，防止 Agent 自己造词，等 MVP-1 有真实跨区数据时再启用。
- **公共安全类内容（天气、交通、公共服务）可以由运营决定全量发送。**
  规则只负责给出"兴趣相关"的名单，不负责替运营决定要不要广播。
- **无回复永远不算负面证据。** 规则里没有任何一条依赖"居民没回",
  也不要让模型自行引入。

## 自检

```bash
python3 tools/validate_demo_data.py                 # 全量校验 + 剧情不变量
python3 tools/validate_demo_data.py --explain C003  # 看某条内容的逐人判定和理由
python3 tools/validate_demo_data.py --explain C003 --after-quick-capture
```

`--explain` 的输出可以直接和 WorkBuddy 里 Agent 的实时结果对照。
不一致就说明 Prompt 漂了，或者规则被改过而没同步。

唯一例外是服务类内容：那里 `--explain` 给的是候选集合，
Agent 做完能力级核对后结果可以更窄。更宽则说明 Agent 跳过了核对。
