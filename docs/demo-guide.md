# MVP-0 Demo 演示手册

> 对应需求文档：`PRD v0.4.1 — MVP-0 Demo Hardening Baseline`
> 判定规则：`config/recommendation-rules.md`

## 1. 这场演示要证明什么

25 位居民、15 条内容。整场演示只讲一件事：

> **系统不是为了多发，而是为了发对；而且它会随着每一次真实互动，改变自己的判断。**

四个支撑点：

1. 原始生活信息可以被自动整理成结构化内容；
2. 同一条内容，系统能说清该发给谁、不该发给谁，以及为什么；
3. 一次现场记录的互动，会立刻改变下一轮推荐结果；
4. 接不住的居民需求会沉淀下来，变成东湖的服务引入 / 招商线索。

## 2. 演前准备

```bash
# 1. 如果演示日期不是 demo/anchor.txt 里的日期，先平移
python3 tools/shift_demo_dates.py --to <演示日期> --write

# 2. 校验，必须全绿
python3 tools/validate_demo_data.py

# 2b. 线上词表体检 —— Agent 可能已经悄悄新建过选项（T0 B3）
python3 tools/mcp_payloads.py check-options

# 3. 打印预期结果，演示时拿来和 Agent 实时输出对照
python3 tools/validate_demo_data.py --explain C001
python3 tools/validate_demo_data.py --explain C003
python3 tools/validate_demo_data.py --explain C003 --after-quick-capture
python3 tools/validate_demo_data.py --explain C005
python3 tools/validate_demo_data.py --explain C011
```

`--explain` 的输出就是这套规则的标准答案。
Agent 的实时结果和它对不上，说明 Prompt 漂了或者数据被改过——**在彩排时发现，不要在现场发现**。

> 唯一例外：服务类内容（C009、C010）的 `--explain` 给的是**候选集合**，
> Agent 还要做能力级核对，结果可以更窄。这两条不在演示动线上，只在表里做背景。

## 3. 五位关键角色

| 居民 | 角色 | 关键设置 |
|---|---|---|
| `R003 张姐` | Before / After 主角 | `identify_note = 3栋张姐`；`long_term_interests = 社区活动`；`recent_interests` 为空 |
| `R009 陈叔` | NO_SEND | `long_term_interests = 买菜生鲜;社区活动`；`avoid_topics = 优惠促销` |
| `R014 王阿姨` | 未满足需求 | `recent_needs` 为空，现场才产生助浴 Need |
| `R018 小刘` | 今日不触达 | `status = low_active`，今天有负反馈 |
| `R021 李阿姨` | 东湖内容精准触达 | 近期买菜信号 + 对早市的正反馈 |
| `R017 东门张姐` | 重名消歧 | 和 R003 同名，用来证明不会认错人 |

## 4. 演示脚本（5–10 分钟）

### Step 1 · 内容结构化（约 1 分钟）

粘一段原始信息给 Content Agent，展示它整理出标题、摘要、标签、适用人群、
时效和商业属性。

**要说的话**：这一步替掉的是运营每天复制粘贴、手工分类的活。

### Step 2 · 推荐 + NO_SEND（约 2 分钟）

先跑 `C001 东湖周末时令菜早市`：

```text
SEND 8 人：R003 张姐、R004 刘阿姨、R009 陈叔、R014 王阿姨、
          R016 杨叔、R019 蒋女士、R021 李阿姨、R025 周阿姨
```

25 个人里发 8 个，每个都有具体依据。

再跑 `C005 东湖商户周末满减促销`：

```text
SEND 3 人：R004 刘阿姨、R021 李阿姨、R025 周阿姨
NO_SEND ：R009 陈叔 —— 明确把「优惠促销」设为不想收的内容
          R018 小刘 —— 同上，且今天刚说过消息太多
```

**这里是整场演示的第一个记忆点**，一定要说透：

> 陈叔长期关注买菜生鲜，按兴趣他本来该收到这条满减。
> 但他说过不想收促销，所以系统不发。
> 而刚才那条东湖早市，陈叔是收得到的——**不是把人屏蔽了，是按内容判断的**。

同一个人在两条内容上的相反结论，比任何解释都有力。

### Step 3 · 张姐 Before / After（约 2 分钟，全场核心）

**Before** — 跑 `C003 周末儿童自然体验活动`：

```text
SEND 5 人：R001 李女士、R010 孙女士、R015 彭女士、R019 蒋女士、R024 龙女士
NO_SEND ：R006 王老师 —— 已经报名了，不重复打扰
名单里没有 R003 张姐。
```

**要说的话**：系统不是不认识张姐——刚才那条东湖早市她就在名单里。
只是在"孩子"这件事上，系统目前一条依据都没有。

**Quick Capture** — 现场输入：

```text
3栋张姐问最近有没有适合小学生周末参加的活动。
```

Ops Agent 应当：匹配到 `R003`（不是东门张姐）→ 生成 Interaction 草稿 →
建议 `recent_interests += 亲子活动` → 运营确认写入。

> 可以顺手演一下消歧：只输入「张姐问…」，系统会列出两位候选让你选。
> 这一下能消掉观众心里"它会不会认错人"的疑问。

**After** — 对同一条 `C003` 重新推荐：

```text
SEND 6 人：多了 R003 张姐
理由：张姐刚刚主动问过适合小学生参加的周末活动。
```

**要说的话**：内容没变，规则没变，改变的只有一次真实互动。
这就是"越用越懂"的具体样子——它不是一句形容词，是名单上多出来的一个人。

> 不要改历史的 P003。新建一条 P007 作为 After 草稿，
> 两条并排放在表里，Before 和 After 可以直接对着看。

> **如果观众问"那不想被打扰的人怎么办"**，可以顺手翻到 P006（羽毛球活动）：
> 小刘长期关注运动健身，这条内容是适合他的，所以他出现在 `hold_residents` 里；
> 但他今天刚说过消息太多，所以不在当天的执行名单上。
> **适合、但今天不发** —— 这和陈叔的"这个主题就别发了"是两回事。

### Step 4 · 王阿姨的需求（约 1–2 分钟）

现场输入：

```text
4栋王阿姨想找周末可以上门的老人助浴服务。
```

Ops Agent：匹配 `R014` → Interaction + Need → 查 Services →
`unable_to_resolve`。

**要说的话**：服务库里有老人陪诊，但那是陪去医院，不是上门助浴。
系统没有硬凑一个服务糊弄过去，而是记下来：**这件事我们现在接不住**。

而且它不是被划掉了——这条需求仍然算"未满足"。
等东湖真的引进了上门助浴，王阿姨会第一批重新进入候选。
**接不住的需求，恰恰是最有价值的那部分数据。**

### Step 5 · 今日运营摘要 + 东湖机会（约 1–2 分钟）

问："今天我最应该关注什么？"

预期包含：

- 今天有几条内容值得发，分别发给多少人；
- 张姐刚刚新增了亲子关注；
- 小刘今天不要主动触达；
- 王阿姨的助浴需求没有供给；
- **重复出现但当前没有供给的需求**：老人上门服务（助浴、理发、半日照护）、
  儿童周末托管、小家电维修——可作为东湖的服务引入和招商线索。

**收尾的话**：前面四步是帮运营人员省时间、少出错。
这一步是把每天的居民对话，变成东湖可以拿来做决策的东西。

## 5. 彩排检查清单

至少连续跑 3 次，每次确认：

1. MCP 读取正常，25 条居民一次读全（`list_records` 必须传 `field_titles`）；
2. Quick Capture 匹配到 `3栋张姐`(R003)，不是东门张姐(R017)；
3. C003 Before 是 5 人且不含 R003，NO_SEND 是王老师；
4. C003 After 是 6 人且含 R003，理由引用刚才那条互动；
5. C005 对 R009 输出 NO_SEND，理由是 avoid_topics；
6. C001 的 SEND 名单里有 R009；
7. 王阿姨的助浴需求判为 `unable_to_resolve`，没有被匹配到 S006；
8. 今日摘要提到未满足需求和招商线索。

每次记录耗时，填进 `docs/rehearsal-log.md`。

## 6. 三层兜底

| 方案 | 什么时候用 |
|---|---|
| Plan A 实时演示 | 默认 |
| Plan B 预置状态 | 某一步 MCP 或模型卡住 → 切到已备好的 `Demo_After` 副本继续讲 |
| Plan C 完整录屏 | 现场网络或平台异常 → 放 5–10 分钟录屏 |

演前保留两份副本：`东湖生活圈_Demo_Before`、`东湖生活圈_Demo_After`。

## 7. 对外表达

**不要讲**：MCP、Agent 数量、SmartSheet、Prompt、数据库、规则引擎。

**只讲**：

> AI 帮运营人员每天找出真正值得居民知道的信息，判断什么适合谁，
> 并随着居民互动，逐渐理解这个社区真正需要什么。

## 8. 数据纪律

- `resident_id` 不修改；
- Interactions 只追加，不为还原演示改历史 `raw_note`；
- 重新彩排时用 Demo Before 备份重新开始；
- 改完任何 seed 数据，跑一次 `python3 tools/validate_demo_data.py`。
